# 核心设计

本文说明 LrmneCode 的整体结构与关键机制。术语定义见 [`CONTEXT.md`](../CONTEXT.md)，
历史取舍见 [`docs/adr/`](adr)。

---

## 1. 总体思路

LrmneCode 把「终端界面」和「智能体内核」拆成两个进程：

- **前端进程**（`frontend/`）负责 TUI：渲染、输入、命令面板、浮窗。
- **后端进程**（`proxy_layer/` + `handlers/` + `backend/`）负责 AgentScope 智能体：
  模型调用、工具执行、状态持久化。

两者通过标准输入输出上的一行一条 JSON 协议通信。这样做的好处是：前端不 import 任何
后端业务代码，后端崩溃或不回帧不会连累界面，且两边可以各自独立测试。

```
┌─────────────────────────┐        stdin: command         ┌──────────────────────────┐
│      前端进程 (TUI)      │ ───────────────────────────▶ │       后端进程            │
│  frontend/              │                              │  proxy_layer/            │
│   - LrmneCodeApp        │ ◀─────────────────────────── │   - Runtime → Scheduler  │
│   - ConversationStore   │   stdout: event / receipt    │   - Executor → handlers  │
│   - BackendClient       │                              │  handlers/ → backend/    │
└─────────────────────────┘                              └──────────────────────────┘
                            stderr: 日志尾部（供报错展示）
```

## 2. 分层与依赖方向

| 层 | 目录 | 职责 |
|---|---|---|
| 界面层 | `frontend/` | TUI 组件、命令、事件渲染、协议客户端 |
| 协议与调度层 | `proxy_layer/` | 行协议 schema、Runtime 主循环、调度、执行、注册表 |
| 业务 operation 层 | `handlers/` | 把每个 `namespace.operation` 绑到一个带 Pydantic 参数模型的 handler |
| 后端装配层 | `backend/` | AgentScope Agent 组装、工作区、模型配置、权限、快照，以及 `adapter/` 对上层暴露的函数 |

依赖方向自上而下单向：`frontend → proxy_layer → handlers → backend`。

**关键边界**：`backend/`、`handlers/`、`proxy_layer/` 中没有任何一处 import `frontend`。
前端是自包含的（见 [ADR-0001](adr/0001-前端大文件拆成包.md)）。

## 3. 进程模型

后端没有独立的 `__main__` 入口，由前端用 `python -c` 引导启动（见
[`frontend/client.py`](../frontend/client.py) 的 `_BOOTSTRAP`）：

```python
import asyncio
_orig_spawn = asyncio.create_subprocess_exec
def _patched_spawn(*args, **kwargs):
    kwargs.setdefault("stdin", asyncio.subprocess.DEVNULL)
    return _orig_spawn(*args, **kwargs)
asyncio.create_subprocess_exec = _patched_spawn

from proxy_layer.runtime import Runtime
asyncio.run(Runtime().run())
```

引导脚本里对 `create_subprocess_exec` 打补丁注入 `stdin=DEVNULL`，是一条必要的
workaround：AgentScope 工具链内部 spawn 的 python shim 未显式设置 stdin，会继承后端
的管道 stdin 并卡住不退出，导致 `chat.send` 永远没有事件回来。

`BackendClient` 的相关约定：

- 子进程的 cwd 用**启动时所在目录**（即用户的项目根），导入路径靠 `PYTHONPATH` 指向源码根，不依赖 cwd。
- 启动完成前发出的命令会暂存，启动后自动补发。
- `stdout` 按行读，解析成 `EventProtocol` 或 `ReceiptProtocol` 分发；无法解释的行包装成错误回执。
- StreamReader 上限放宽到 32MB：`Glob` / `Grep` 的一整块结果就是一行 JSON，默认 64KB 上限会让读行直接抛错并把泵打死。
- 退出时先关 stdin 让后端读到 EOF，超时后逐级 `terminate` → `kill`。

## 4. 通信协议

协议定义在 [`proxy_layer/schema.py`](../proxy_layer/schema.py)，共三种消息，`message_type` 字段固定不变：

| 消息 | 方向 | 用途 |
|---|---|---|
| `CommandProtocol` | 前端 → 后端 | 一次操作请求，带 `request_id` / `operation` / `parameters` |
| `ReceiptProtocol` | 后端 → 前端 | 命令回执，`accepted` 表示成功或失败，成功可带 `result` |
| `EventProtocol` | 后端 → 前端 | 单向推送，无配对无回执，带 `event` / `data` |

回执的形状由模型校验器强约束：成功时不得携带 `error_code`，失败时必须给出 `error_code` 且不得携带 `result`。

**标识符**：

- `conversation_id`：前端在进程启动时生成一次（`c-<8位十六进制>`），后端只透传不生成。
- `request_id`：前端模块级计数器自增（`req-1`、`req-2`…），保证本次运行内唯一；后端只回显。

**错误码**（`ErrorCode`）与业务无关，只描述「这次命令为什么失败」：
`invalid_message`、`unknown_operation`、`invalid_parameters`、`busy`、`cancelled`、`internal_error`。

## 5. 调度与执行

### 5.1 命令模式

每个 operation 注册时声明一种 `CommandMode`：

| 模式 | 行为 |
|---|---|
| `PLAIN` | 直通执行，不参与排队（默认） |
| `WAIT` | 按会话 FIFO 排队，等前序 `WAIT` 命令执行完 |
| `CONTROL` | 管理动作：执行前先中断本会话的在途与排队命令 |

典型用法：`chat.send` 是 `WAIT`（同一会话的对话必须串行），`chat.interrupt` 是 `CONTROL`
（先取消在跑的对话，自己再执行）。

### 5.2 调度流程

[`proxy_layer/scheduler.py`](../proxy_layer/scheduler.py) 的 `submit(msg)` 是一个 async 生成器：

1. 查注册表拿到 operation 与其模式。
2. 若是 `CONTROL`，先 `cancel_pending(conversation_id)`。
3. 若**不是** `WAIT`，直接交给 Executor 执行并逐块产出。
4. 若是 `WAIT`，挂到本会话队尾；若前面还有未完成的 `WAIT`，先发一条 `run.queued` 事件，再 `await` 前驱；前驱被取消则回 `cancelled` 回执并结束。

### 5.3 执行器

[`proxy_layer/executor.py`](../proxy_layer/executor.py) 按 handler 类型区分产出：

- **生成器 handler**（同步或异步）：先发一条成功回执，再逐块转发产出，最后发 `run.finished`
  （`stop_reason` 为 `completed` / `error` / `interrupted`）。
- **普通函数 handler**：只发一条携带 `result` 的成功回执（或 `INTERNAL_ERROR` 回执）。
- 参数在进入 handler 前先用 `params_model.model_validate` 校验，失败回 `invalid_parameters`。

### 5.4 Runtime

[`proxy_layer/runtime.py`](../proxy_layer/runtime.py) 是后端主循环：从 stdin 逐行读、解析协议，
只处理 `command` 消息（其余忽略），每条命令起一个异步任务执行，把每条产出序列化成一行写回 stdout。
整行无法解析时回 `invalid_message`（此时还没有会话/请求 id）。

产出会被 `_as_frame` 收成协议帧：已是 `BaseProtocol` 的原样返回，`dict` 按 `{event, data}`
包装成事件。

## 6. 注册表机制

### 6.1 后端：operation → handler

[`proxy_layer/register.py`](../proxy_layer/register.py) 提供 `register_command(namespace, operation, mode)`。
被注册的函数有严格签名约束：**恰好一个参数，参数名必须是 `params`，类型必须是 `BaseModel` 子类**，
否则注册时立即抛 `TypeError`。注册表按 `namespace.operation` 组织，`lookup()` 解析该字符串。

各业务命名空间有便捷注册器：`chat_register`、`config_register`、`approval_register`、
`session_register`、`diff_register`、`skill_register`、`mcp_register`。

[`handlers/__init__.py`](../handlers/__init__.py) 导入各模块即完成注册（副作用注册表），
Runtime 只需 `import handlers`。

### 6.2 前端：operation → 结果呈现，event → 事件渲染

[`frontend/registry.py`](../frontend/registry.py) 与后端镜像：

- `@operation("config.get")` 注册「成功回执的 `result` 怎么呈现」，写在 [`frontend/results.py`](../frontend/results.py)。
- `@event("stream.text")` 注册「事件怎么渲染」，写在 [`frontend/events.py`](../frontend/events.py)。
- `declare_operation(...)` 登记没有结果渲染器的 operation（如 `chat.send`、`approval.respond`），可标记 `stream=True`。

UI 壳只做查表分发，不出现 `kind` 之类的字符串分支。这两个模块也是**导入即注册**，
`frontend/app/main.py` 必须保证 `from .. import events`、`from .. import results` 这类副作用导入执行过一次。

## 7. 事件翻译

AgentScope 的事件对象不能直接过协议（可能很大、类型繁多）。
[`backend/adapter/translate.py`](../backend/adapter/translate.py) 的 `translate(event)` 把
AgentScope 事件逐一映射成 `{event, data}`，**不认识的事件返回 `None`（不透传）**。

主要事件族：`reply.*`、`model.*`、`stream.text.*`、`stream.thinking.*`、`stream.data.*`、
`stream.hint`、`tool.call.*`、`tool.result.*`、`approval.request`。

两处值得注意的处理：

- `tool.result.delta` 只发文本**尾部**（`_RESULT_DELTA_TAIL = 64000`）：整块几 MB 的工具输出
  不该原样变成一行协议消息，前端预览行只需要尾部那一段。
- `approval.request` 由 `RequireUserConfirmEvent` 译出，是审批流程的入口。

## 8. 后端装配

### 8.1 Agent 构建

[`backend/factory.py`](../backend/factory.py) 的 `build_agent(workspace, state)` 按当前配置组装 Agent：

- 未配置模型时抛 `RuntimeError`（前端会据此提示先配置）。
- `chat_model` 由 `model_config._build_model()` 按提供方 / 凭证 / 思考级别 / 上下文窗口构建。
- 组装后把权限模式挂到 Agent 的 `permission_context`，并把项目根挂为额外工作目录。

### 8.2 工作区

[`backend/workspace.py`](../backend/workspace.py)：

- `ProjectLocalWorkspace`：workdir 落在 `.lrmnecode/`，但把 shell（Windows 用 `PowerShell`，
  其余用 `Bash`）与读写工具的工作目录绑到**项目源码根**，`.lrmnecode` 视为产品元数据而非应用代码。
- `SessionManager`：按 `conversation_id` 持久化 `AgentState` 到
  `.lrmnecode/sessions/<cid>/state.json`，并缓存进程内 live agent。
- `WorkspaceManager`：持有 project_root / code_home，惰性构建工作区与 Toolkit（含 skills、MCP）。

### 8.3 配置

- [`backend/user/model.py`](../backend/user/model.py) 的 `ModelConfig`：模型 / 凭证 / 思考级别 / 上下文窗口，
  读写 `~/.lrmnecode/settings.json`。对外只暴露脱敏视图（api_key 只回 `configured` 与末 4 位）。
- [`backend/user/permission.py`](../backend/user/permission.py) 的 `PermissionConfig`：对齐 AgentScope 的 `PermissionMode`，
  更新时挂到活跃 Agent 上。

`config.set` 会把模型 / 权限变更**热更新到全部活跃会话**（`session_manager.live_agents()`）。

### 8.4 共享状态

[`backend/adapter/_state.py`](../backend/adapter/_state.py) 持有两样包内共享物：
审批挂起表 `_pending_approvals`、当前工作区 `workspace_manager`（切换工作区时只改这里的绑定）。

## 9. 审批流程

1. Agent 推理中触发需确认的工具调用，AgentScope 抛出 `RequireUserConfirmEvent`。
2. [`backend/adapter/chat.py`](../backend/adapter/chat.py) 把它登记进 `_pending_approvals`（`reply_id → Future`），
   并把 `approval.request` 事件透传给前端。此时 `chat.send` 挂起等待。
3. 前端渲染审批面板；用户允许或拒绝后发 `approval.respond`。
4. [`backend/adapter/approval.py`](../backend/adapter/approval.py) 的 `respond_approval` 解开 Future；
   `chat.py` 拿到结果继续 `reply_stream`，直到本轮结束（含中断 / 出错），最后回存状态。

`always=True` 表示「记住这类放行」，由 AgentScope 侧的权限上下文承接。

## 10. 快照与 diff / undo

[`backend/snapshot.py`](../backend/snapshot.py) 的 `SnapshotManager` 在**每一轮对话开始前**
（`begin_round`）快照工作区的文本文件，供 `/diff` 与 `/undo`：

- 快照存 `.lrmnecode/snapshots/<cid>/r<n>/`，每个文件一个 JSON（路径 + 内容），文件名是路径的 md5。
- 只快照可 UTF-8 解码的文本文件，跳过 `.git`、`.lrmnecode`、`__pycache__`、`node_modules`、`.venv` 等目录。
- 每会话最多保留 `MAX_ROUNDS = 20` 轮，超出丢弃最旧轮。

[`backend/adapter/diff.py`](../backend/adapter/diff.py) 基于快照提供三个操作：

- `diff.list`：列出本会话有快照的轮次。
- `diff.show`：快照 vs 当前文件，生成 unified diff。
- `diff.undo`：把某轮快照写回磁盘（按轮次整体恢复）。

## 11. 前端应用结构

[`frontend/app/main.py`](../frontend/app/main.py) 的 `LrmneCodeApp` 由若干 mixin 组合而成：

| mixin | 职责 |
|---|---|
| `SessionsMixin` | 会话生命周期与配置落地 |
| `ProtocolMixin` | 命令下发、事件 / 回执分发、流式合并、后端退出 |
| `InteractionMixin` | 提交、斜杠命令、内联面板导航、附件 |
| `MentionsMixin` | `@` 提及候选、工作区文件、skill |
| `OverlaysMixin` | 四种浮窗的开启与关闭 |
| `ApprovalMixin` | 审批表态、`Esc` 中断 |

**框架约束**：`@on(...)` 装饰的处理器与 `BINDINGS` **必须留在 App 类自身**，不能搬进普通 mixin ——
Textual 只从类自己的 `__dict__` 收集装饰过的处理器，放 mixin 里会静默失效（见
[ADR-0003](adr/0003-App类拆分必须保留@on入口.md)）。因此这 6 个 `@on` 入口是留在
`app/main.py` 里的薄入口，其余方法靠正常属性查找调用。

前端目录同样按职责拆包：`widgets/`、`overlay/`、`app/`，每个模块控制在 400 行以内，
外部导入路径由各包 `__init__.py` 转发（见 [ADR-0001](adr/0001-前端大文件拆成包.md)）。

## 12. 目录与数据布局

```
~/.lrmnecode/                 # 全局（跨项目）
└── settings.json             # 模型 / 凭证

<项目根>/.lrmnecode/           # 项目级
├── sessions/<cid>/state.json # 会话状态存档
├── snapshots/<cid>/r<n>/     # 每轮快照（diff / undo）
├── skills/                   # 项目级 Skills
└── mcp/                      # MCP 服务器配置
```

全局配置与项目元数据分开，是因为模型凭证属于用户，而会话 / 快照属于具体项目。
