# 开发者指南

面向要修改或扩展 LrmneCode 的开发者。架构与机制细节见 [核心设计](核心设计.md)，
术语定义见 [`CONTEXT.md`](../CONTEXT.md)。

---

## 1. 环境搭建

```bash
# 创建虚拟环境并安装（含开发依赖）
python -m venv .venv
.\.venv\Scripts\Activate.ps1        # Windows
# source .venv/bin/activate          # macOS / Linux

pip install -e ".[dev]"
```

- Python 要求 **3.11+**（项目用到 `StrEnum`、`X | None` 等特性）。
- 构建系统是 setuptools（`pyproject.toml`），包发现规则覆盖
  `frontend*`、`backend*`、`handlers*`、`proxy_layer*`。
- 运行测试：`pytest test`。

## 2. 目录结构

```
frontend/            # 界面层：TUI 组件、命令、协议客户端
├── app/             # LrmneCodeApp 与 mixins（main.py 保留 @on 入口）
├── overlay/         # 浮窗：picker / prompt / model_config / sessions
├── widgets/         # 部件：transcript / tool_view / approval / side / status / input / usage
├── client.py        # BackendClient：拉起后端子进程，行协议读写
├── commands.py      # 斜杠命令注册表
├── registry.py      # 前端分发注册表（operation → 结果呈现，event → 渲染）
├── events.py        # 事件渲染器（导入即注册）
├── results.py       # 结果渲染器（导入即注册）
├── conversation.py  # 会话运行态与视图
├── mentions.py      # @ 提及纯逻辑
├── theme.py         # 主题与样式常量
└── tools.py         # 工具视图的纯逻辑

proxy_layer/         # 协议与调度层
├── schema.py        # 协议消息定义与构造/序列化
├── runtime.py       # 后端主循环：读行、解析、分发、写回
├── scheduler.py     # 按 CommandMode 调度
├── executor.py      # 执行 handler，产出回执/事件
├── register.py      # operation 注册表
├── transport.py     # stdin/stdout 行读写
└── session.py       # conversation_id 的 ContextVar

handlers/            # 业务 operation 层（一个文件一个命名空间）
└── chat.py config.py approval.py session.py diff.py skill.py mcp.py

backend/             # 后端装配层
├── factory.py       # build_agent
├── workspace.py     # 工作区、会话状态、Toolkit
├── snapshot.py      # 每轮快照（diff / undo）
├── developer/prompt.py   # Agent 名称与系统提示词
├── user/model.py         # 模型 / 凭证配置
├── user/permission.py    # 权限模式配置
└── adapter/         # 对 handlers 暴露的函数门面 + 事件翻译

test/                # 测试：backend / frontend / handlers / integration / proxy_layer / system
docs/                # 文档：核心设计 / 开发者指南 / 用户指南 / adr / specs
```

**依赖方向**：`frontend → proxy_layer → handlers → backend`，
后端三层不得反向 import `frontend`。新增代码时保持这个方向，不要把后端逻辑漏进前端。

## 3. 开发约定

- **术语以 `CONTEXT.md` 为准**。「治理」「功能」「渲染快照基线」「切片」在本项目有特定含义，
  改动涉及这些词时先读术语表。
- **注释写「为什么」，不写「是什么」**。仓库里的注释大量记录踩坑原因（workaround、时序陷阱、
  框架行为），沿用这个风格；能用代码表达清楚的不要加注释。
- **前端单模块 ≤ 400 行**，由 `test/test_frontend/test_structure.py` 守卫。超了按职责继续拆，
  不要抬高上限。
- **`@on` 处理器与 `BINDINGS` 留在 App 类自身**（放 mixin 会静默失效）。
- **命令不带参数**。斜杠命令只负责「打开选择卡片」或「发一条协议命令」，取值由 `Picker` / `Prompt` 兜住。
- **协议只走 `proxy_layer/schema.py`**。前端不直接拼 JSON，后端不绕过构造器。

## 4. 扩展指南

### 4.1 新增一个后端 operation

以「新增 `echo.ping`」为例，分三步：

**① 在 `backend/adapter/` 写实现**（纯函数或 async 函数），并导出：

```python
# backend/adapter/echo.py
def ping(rounds: int) -> dict:
    return {"pong": rounds}

# backend/adapter/__init__.py
from .echo import ping
__all__ = [..., "ping"]
```

**② 在 `handlers/` 注册 handler**（参数模型 + 注册装饰器）：

```python
# handlers/echo.py
from pydantic import BaseModel
from proxy_layer.register import echo_register   # 见下方说明
from backend.adapter import ping

class EchoPingParams(BaseModel):
    rounds: int = 1

@echo_register("ping")
def echo_ping(params: EchoPingParams) -> dict:
    """一次 ping；round 决定回几轮。"""
    return ping(params.rounds)
```

**③ 导入即注册**：在 [`handlers/__init__.py`](../handlers/__init__.py) 里 `from . import echo`。

两个注意点：

- 注册器按命名空间提供。若命名空间已存在（如 `chat`），直接用 `chat_register`；若是新命名空间，
  先在 [`proxy_layer/register.py`](../proxy_layer/register.py) 补一个 `echo_register = lambda operation, mode=CommandMode.PLAIN: register_command("echo", operation, mode)`。
- handler 的签名约束：**恰好一个参数、名为 `params`、类型是 `BaseModel` 子类**，否则注册即报错。
  流式操作（逐块产出）用生成器函数，模式选 `WAIT`；管理类动作用 `CONTROL`，普通读写用默认 `PLAIN`。

### 4.2 新增一个前端斜杠命令

在 [`frontend/commands.py`](../frontend/commands.py) 用 `@command` 注册：

```python
@command("echo", "示例命令", aliases=("ec",))
def cmd_echo(app: "LrmneCodeApp") -> None:
    app.notify_line("hello", "info")
```

约定：

- 命令**不吃参数**。要选值就弹卡片：

  ```python
  app.open_picker("echo", "选择回响次数", choices=[...], current=..., on_select=lambda v: ...)
  ```

- 要发协议命令就 `app.send("echo.ping", {"rounds": 2})`。
- 结果呈现写好之后，配合 `frontend/results.py` 里的注册把回执渲染出来（见 4.3）。

### 4.3 新增事件 / 结果渲染

后端推送的事件，在 [`frontend/events.py`](../frontend/events.py) 注册：

```python
@event("echo.pong")
def _render_pong(app, conv, data) -> None:
    conv.view.add(NoticeLine(f"pong {data['rounds']}", "info"))
```

命令的成功回执，在 [`frontend/results.py`](../frontend/results.py) 注册：

```python
@operation("echo.ping", label="回响")
def _show_ping(app, conv, result) -> None:
    app.notify_line(f"pong: {result}", "success")
```

补充规则：

- 没有结果渲染器的操作，用 `declare_operation("echo.ping", label="回响")` 登记，让状态栏能显示正确的
  操作名；流式操作加 `stream=True`。
- `events.py` / `results.py` 是**导入即注册**的，新增注册后不用改 `app/main.py`，它已经副作用导入了这两个模块。
- 后端新增事件名后，前端记得在 `events.py` 注册，否则会静默丢弃。

### 4.4 新增配置项

- 模型相关：改 [`backend/user/model.py`](../backend/user/model.py) 的 `_UPDATE_HANDLERS` 与 `MODEL_CONFIG_KEYS`，
  并在 `config.set` / `config.get` 的路由里出现。
- 权限相关：改 [`backend/user/permission.py`](../backend/user/permission.py)。
- 取值域面向用户的说明（下拉候选、注释）写在前端命令里，如 [`frontend/commands.py`](../frontend/commands.py)
  的 `PERMISSION_MODES` / `THINKING_NOTES` / `CONTEXT_SIZES`。

## 5. 测试

### 5.1 运行

```bash
pytest test                 # 全量
pytest test/test_frontend   # 只跑前端
pytest test/test_backend    # 只跑后端
pytest test -k workspace    # 按关键字筛选
```

`pyproject.toml` 已配置 `testpaths = ["test"]`、`pythonpath = ["."]`，直接在仓库根运行即可。

### 5.2 结构

| 目录 | 覆盖 |
|---|---|
| `test/test_frontend/` | TUI 壳、命令、事件渲染、会话切换、快照 |
| `test/test_backend/` | adapter、权限、模型配置、快照、工作区 |
| `test/test_handlers/` | handler 注册与配置 |
| `test/test_proxy_layer/` | schema、Runtime、调度、执行、注册、传输 |
| `test/test_integration/` | 端到端管线 |
| `test/test_system/` | 命令循环 |

### 5.3 前端测试的接缝

前端主应用壳需要 `BackendClient`，测试里由
[`test/test_frontend/conftest.py`](../test/test_frontend/conftest.py) 的 `make_app` 夹具换成不拉子进程的
`FakeClient`：命令留在 `client.sent` 里，事件 / 回执由测试手工投喂（`emit()` / `_handle_receipt()`），
用 `app.run_test()` + `pilot.pause()` 驱动。

> **patch 目标必须是「调用处所在的模块」**：`monkeypatch.setattr(app_main, "BackendClient", FakeClient)`。
> `from X import name` 绑的是各模块自己的命名空间，拆包后只打顶层包名会**静默失效**。

### 5.4 渲染快照基线

前端治理的验收依赖**渲染快照**（含样式的 SVG），基线在 `test/test_frontend/snapshots/`。
它专门用来抓行为断言抓不到的回归：CSS 作用域被改写、挂载晚一拍、字形退化等。

- 机制：`App.export_screenshot()`，固定终端尺寸 `(120, 40)`。
- 比对前会折掉随机样式类名、每次启动重生的会话号、耗时与动画。
- 重新生成全部基线：

  ```bash
  LRMNE_SNAPSHOT_UPDATE=1 pytest test/test_frontend
  ```

  （Windows PowerShell：`$env:LRMNE_SNAPSHOT_UPDATE=1; pytest test/test_frontend`）

**只在你确实有意改变外观时才更新基线**；否则基线变化就是回归信号。

### 5.5 结构守卫

[`test/test_frontend/test_structure.py`](../test/test_frontend/test_structure.py) 钉住两条治理成果：

- 前端每个 `.py` ≤ 400 行。
- `@on` 处理器（`Submitted` / `TabPressed` / `PaletteNavigate` / `Changed` / `Decision` / `OptionSelected`）
  与四个键位（`escape` / `f2` / `f3` / `ctrl+q`）仍在 App 类自身。

## 6. 调试

**前端**：后端进程的 stderr 末尾会被收集，前端退出时展示在转录区（`Card("stderr", ...)`）。
后端崩溃通常会显示「后端进程已退出 (code=...)」并附上尾部日志。

**后端**：它由前端用 `python -c` 拉起，无法单独启动。要单独调试某个 handler，
可以直接 import `backend.adapter` 里的函数，或写一个一次性脚本调用它。

**协议帧**：所有帧都是一行 JSON。排查时可以在 `proxy_layer/transport.py` 的
`write_line` 或 `frontend/client.py` 的 `_pump_stdout` 临时打印行，看清发了什么、收到什么。

**常见坑**：

- 前端收不到任何帧、状态栏一直「运行中」——先看是不是某一行 JSON 超过了流上限（客户端已放宽到 32MB）。
- 改了 handler 却没生效——检查 `handlers/__init__.py` 是否导入了该模块（不导入就不注册）。
- `@` 提及 / 命令面板不响应——检查你的处理器是不是写进了 mixin（`@on` 必须留在 App 类）。

## 7. 提交与治理

本项目的结构重构遵循「**治理**」的约定（见 [`CONTEXT.md`](../CONTEXT.md)）：只改代码结构，
不改用户可观察的行为与外观。

- 一次「切片」＝一个自底向上的提交单元：拆一个包 → 跑全量测试 + 快照比对 → 全绿才提交。
- 顺序由依赖方向决定：叶子先拆，最上层最后。
- 一个切片只做搬运，不做行为变更；发现的功能缺陷记入清单，另开一轮。
- 关键且不可逆的决策写进 [`docs/adr/`](adr)，规格写在 [`docs/specs/`](specs)。

完整的治理规格与落地差异见 [specs/2026-09-22-前端结构治理.md](specs/2026-09-22-前端结构治理.md)。
